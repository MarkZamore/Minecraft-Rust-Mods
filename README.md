# Minecraft Rust Mods

Отдельная сборка для Windows x64 на Horizon, нативной реализации Minecraft Java Edition 26.3 на Rust. Её ID в LANMinecraft — `minecraft-10`, каталог установки — `Minecraft Rust Mods`. Bootstrap самостоятельно получает закреплённые файлы Minecraft 26.3 и Java 25, проверяет их контрольные суммы и подготавливает ресурсы в собственном кеше. Другие установленные сборки не требуются. Версия клиента и Steam-ревизия закреплены в `portable-pack.json`. После изменения активного состава надо обновить Steam-ревизию, чтобы два разных состава не подключались друг к другу.

Для подтверждённого сбоя запуска с неявным Vulkan-слоем Overwolf сборка хранит `DISABLE_VULKAN_OW_OVERLAY_LAYER=1` в `launcher/environment-defaults.json` и передаёт его как `native/presentation.json:environmentDefaults`. Это адресное значение по умолчанию для процесса игры по [контракту Khronos disable_environment](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderLayerInterface.md). Общий bootstrap применяет его только при отсутствии унаследованной переменной; личное значение, включая пустое, и явные `Command.env`/`env_remove` имеют приоритет. Steam-слой, выбор графического backend и игровые расстояния сохраняются. Реестр Windows, системные переменные и чужие процессы эта политика не меняет.

Сборка включает проверенный bootstrap и Steam-слой из исходников Minecraft Rust Edition. Точная база закреплена в `tools/base-lock.json`; текущий рецепт использует Horizon Nightly `2ebf00a` и проверенный Steam-компонент `89b0ce8`. Самостоятельная подготовка ресурсов из прежних баз `597328c` и `4757a85` сохранена. Копия Rust Edition на компьютере игрока не требуется. Компоненты модов принадлежат этому репозиторию. `.hnmod` встраиваются в клиент при сборке, `.hmod` загружаются из проверенной поставки. Horizon сверяет SHA-256 архивов контентных модов при сетевом входе. Миры, настройки графики и `options.txt` остаются личными данными игрока.

Пресет управления лаунчера содержит 62 базовых назначения Horizon 26.3 и три назначения модов: `Insert` для колеса Orbital Laser, `F7` для создания точки Waypoints и `F8` для списка точек. Всего 65 назначений; `M/N/R` Horizonmatica сохраняются. Сочетания модов настраиваются в самой игре. [Раскладка и границы проверки](tools/CONTROLS.md).

[Состав и описания компонентов](MODS.md).

## Orbital Laser и существующие миры

В сборке 37 нативных модов. Обновление доступно через обычную кнопку «Играть» в LANMinecraft. В творческом режиме команда `/orbital give` выдаёт целеуказатель. Когда он в руке, колесо удара открывается клавишей Insert из пресета сборки. Разрушение рельефа настраивается в колесе.

Deepbore Quarry и Wayfarer Stones убраны из состава по итогам проверки совместимости. Их блоки в старых мирах могут превратиться в воздух, а предметы могут исчезнуть. Перед первым открытием существующего локального мира клиент создаёт штатную резервную копию ZIP в папке игры `backups`. При создании нового мира клиент записывает только маркер этой версии состава.

При первом запуске Horizon показывает экран специальных возможностей, затем мастер настройки PhysicsModHorizon. Кнопка «Диктор» на первом экране отключена.

Speedrun Timer, Keystrokes и Server Atlas удалены по запросу игрока. Их личные настройки и записи сохраняются. Список Steam-миров использует штатное меню Horizon с общим Steam-слоем сборки.

Автоматический сетевой список по умолчанию показывает только миры Steam. Все сохранённые строки доступны в отдельном явно открываемом разделе сохранённых серверов. Публичные рекомендованные и партнёрские серверы автоматически не добавляются; favicon при просмотре списка автоматически не сохраняется. Политика закреплена в исходниках сборки и повторно применяется при обновлении движка. Существующий личный `servers.dat` и неизвестные поля NBT не очищаются и не переписываются: адрес, название, marker-файл или размер, включая прежние 134 байта, не подтверждают происхождение записи.

## Входы и совместимость

`tools/mod-input-lock.json` фиксирует снимок официального реестра Horizon и точные релизы авторов из `tools/official-mod-sources.json`. `tools/inspect_mods.py` проверяет происхождение, контрольные суммы, подписи при наличии и содержимое архивов. Подробнее о результате инвентаризации в [tools/MOD-INPUTS.md](tools/MOD-INPUTS.md). Записи `candidate` и `compile-probe` подлежат проверке на выбранном Nightly. Карточка строится из проверенного клиентом списка загруженных модов.

`tools/conflict-decisions.json` закрепляет выбор игрока для подтверждённых несовместимостей. Отклонённые версии остаются в lock как проверенные входы для воспроизведения конфликта. Смена версии требует повторного подтверждения совместимости.

Семь проектов с отдельной проверкой условий распространения прошли общий этап планирования. Их компиляция и запуск не проверялись. [Результат планирования](tools/qa/license-review-plan.json).

## Подготовка Windows x64

Понадобятся Python 3.12+, Rust 1.98.1 `x86_64-pc-windows-msvc`, MSVC и Windows SDK. Используйте один зарегистрированный временный стенд LANMinecraft. `$baseSource` — дерево Horizon с проверенным базовым Steam-слоем, `$sourceArchive` — закреплённый подписанный архив Horizon, `$steamTransport` — каталог `source/native` закреплённой версии e4steam. Cargo и тестовый запуск переиспользуют согласованные `$target` и подготовленные игровые ресурсы. Копии миров и ресурсов игрока не требуются.

Для выпуска `$selection` указывает на `tools/mod-selection.json`. Он закрепляет `schemaVersion: 1`, `inputLockSha256` и список `ids`. Перед финальным выпуском в него входят только моды, прошедшие проверки совместимости и лицензий. Сначала примените mixins без `--build`, чтобы получить точную диагностику. `--check` подготавливает исходники и выполняет проверку типов. `--build-prepared` проверяет квитанцию подготовленных исходников и собирает тот же набор.

```powershell
python tools/native_build.py --base-pack $baseRepo --base-source $baseSource `
    --source-archive $sourceArchive --steam-transport $steamTransport `
    --archives $archives --inspection $inspection --selection $selection `
    --work $work --target $target --mixins-root $mixinsRoot --build
```

Обычная сборка проверяет исходные байты и точный Steam-слой, распаковывает архивы в технические копии и применяет официальный `horizon-mixins`. Оригиналы и их подписи сохраняются. Cargo запускается с закреплёнными зависимостями, поддерживаемая конфигурация компиляции и SHA256 результата записываются в `build.json`.

Чтобы подготовить исходники параллельно со сборкой Edition, вызовите `native_build.py` без `--build`. Он проверит исходники и сохранит SHA256 подготовленных деревьев. После фиксации результата Edition запустите ту же команду с `--build-prepared`. Оба клиента используют один каталог Cargo по очереди.

Orbital Laser строится из закреплённого авторского `orbital.hnmod`. Порт хранится в `tools/orbital_compat/`. Из исходных ресурсов и манифеста воспроизводимо собирается `orbital.hmod`. Лаунчер получает этот файл отдельным архивом и переиспользует при обновлениях клиента, пока SHA256 совпадает.

### Самостоятельная подготовка и обновление bootstrap

Первый запуск получает точные клиент, серверный JAR, библиотеки, индекс и объекты ресурсов Minecraft по закреплённым данным Mojang, а также проверенный JDK. Существующая Java Edition может служить источником проверенных файлов только для чтения. При отсутствии установки загрузка идёт с официальных адресов. Повторный запуск проверяет подготовленный кеш. Параметр `--server-jar PATH` из базы `597328c` сохраняется.

При прежнем обновлении только bootstrap клиент с модами и его принятый рецепт не менялись. Обновление движка проверяет заново точный состав и новый клиент. Для восстановления технического `build-work` используйте точные публичные архивы предыдущей ревизии, сверив все записи её манифеста. `runtime/horizon-client.exe`, `content/*.hmod` и уведомления лицензий берутся из проверенной поставки. `build.json` берётся из `tools/qa/final-build.json` и проверяется по `tools/build-lock.json`. Затем используется обычный `stage_mod_pack.py` с новой закреплённой базой. Установленные личные папки игрока не являются входом сборки.

Описание в библиотеке содержит пять игровых предложений по последнему согласованному требованию. `nativeProject` сохраняет имя и ревизию для маршрутизации нативного клиента. Поле ссылки проекта отсутствует, отдельные официальные ссылки модов сохранены в `mod-pages.json`.

### Восстановление опубликованной базы

Если временный кандидат Edition уже удалён, восстановите его из проверенной публичной поставки. `restore_public_base.py` сверяет SHA-256 манифеста, всех трёх архивов, каждого из управляемых файлов и полный distribution lock закреплённого чистого checkout Edition. Дополнительные исходные метаданные библиотеки берутся из того же checkout. Установленные сборки и личные файлы игрока не используются.

```powershell
python tools/restore_public_base.py --base-repo $baseRepo --out "$run/base-public" `
    --manifest-sha256 $acceptedPublicManifestSha256
```

### Обновления от авторов

LANMinecraft устанавливает ревизии из `pack-manifest.json` этого репозитория. Новый выпуск Horizon или мода сначала становится проверяемым входом сборки. Обновите закреплённые версии, хеши и лицензии, затем соберите кандидат штатным `native_build.py`. Правки принадлежат сборке и снова применяются из `tools/`: клики PhysicsModHorizon, JEI в обычном и творческом инвентаре, сетевой порт Orbital Laser, пресет управления и защита существующих миров. Штатный список Steam-миров, гостевые команды, профиль игрока, сообщение об открытии мира и сворачивание меню приходят из закреплённого Steam-слоя Minecraft Rust Edition. Server Atlas в состав больше не входит.

Если исходные байты или точки внедрения поменялись, адаптируйте соответствующую правку к новому коду автора и повторите адресную проверку. Пропуск обязательной правки блокирует выпуск. Хеш рецепта включает код портов, а квитанция сборки связывает его с точным движком, исходными архивами, решениями конфликтов и SHA-256 клиента. Проверка исходников и точек внедрения останавливает сборку при изменении ожидаемого кода автора.

Перед каждым выпуском подготовьте свежие Windows-отчёты для точного EXE: `tools/qa/orbital-startup.json` из полного `smoke_runtime.py`, `tools/qa/multiplayer.json` из `smoke_multiplayer.py --concurrent-effects` и `tools/qa/backup-guard.json` из `smoke_backup_guard.py`. Генератор требует клики PhysicsModHorizon, отключённого «Диктора» при работающей речевой подсистеме, повторное чтение всех 65 клавиш, Insert/R, JEI Creative с поиском и рецептами, гостевые команды с проверкой прав, разрушение мира гостем, эффекты обоих игроков и проверенную резервную копию без сброса личных настроек. Старые квитанции другого EXE, один запуск меню и диагностический `--skip-jei` выпуск не разрешают. Проверка настоящего Steam-оверлея и двух аккаунтов отложена по решению пользователя и отмечается `NOT RUN`; она не подменяется локальным сетевым прогоном. Историческая миграция удалённых блоков также указывается отдельно. Личные настройки и миры хранятся отдельно от управляемых файлов поставки.

`tools/qa/server-policy.json` дополнительно подтверждает шесть обычных запусков: два с чистым профилем, два с восстановленным авторским списком в 134 байта и два с ручным NBT, содержащим неизвестные поля. Восстановленный список является явно обозначенным тестовым образцом из зафиксированных имён/адресов старого клиента, а не копией пользовательского файла. Во всех случаях исходные NBT и существующие marker-файлы должны сохраниться побайтово. В каждом запуске проверяются Steam по умолчанию, все строки в Saved, обновление обоих разделов, явный переход в Steam, возврат Back/Escape в главное меню и повторное открытие со Steam. SHA файла сверяется после каждого действия. Управление QA включается только через `horizon-extras.txt` технического профиля. Флаги `--control-socket`, `--control`, `--frames`, `--offscreen` и другие режимы стенда непригодны: авторский код уже пропускает добавление серверов в таких запусках. Этот отчёт также обязателен для точного EXE. `server_seed_compat.py` проверяет полные сигнатуры и тела двух авторских функций добавления серверов и заменяет их только на успешный пустой результат; остальные сетевые функции, записи и marker-файлы не меняются.

Для Escape требуется настоящее нажатие в окне каждого из шести принадлежащих QA клиентов: native control не принимает клавиши на главном экране. Инструмент использует закреплённый `DesktopKeys` из явного `--base-repo` и создаёт запросы в `$serverQa/desktop-keys`. UI-драйвер обслуживает наблюдаемое окно указанного PID и пишет подтверждение только после действия. Gate сверяет исходный SHA помощника, протокол, ID, PID, EXE, заголовок, номер запуска и окно времени 120 секунд. Подтверждение от другого процесса или замена Escape на click/control-команду приёмку не закрывают.

Нативные уведомления лаунчера проверяются через `smoke_native_notices.py` ниже. Это тонкая обёртка общего проверенного инструмента Edition: она использует его конечные снимки, измерения пикселей, HWND и heartbeat, но проверяет прежний состав Mods вместо пустого списка модов. Свой отчёт `native-notices-qa.json` сохранить в `tools/qa/native-notices.json`. Он привязан к SHA клиента/bootstrap, полному payload, build receipt и исходникам общего контракта. Требуются настоящий полный экран, DPI 1/2 без изменения GUI scale, очередь/срок жизни/оборванные файлы, ввод чата и пауза, отсутствие ошибки и уборка fixture. `tools/launcher-notices-lock.json` и `tools/qa/launcher-notices-support.json` закрепляют публичный лаунчер 478 с capability `native-launcher-notices-v1`, его исходники и независимый потоковый SHA-256 публичного EXE; минимальная поддерживающая версия остаётся 477. Это отдельное доказательство поддержки лаунчера, а не игровой прогон Rust.

После изменения этой политики все итоговые отчёты должны соответствовать фактическому SHA `native/presentation.json` и содержать `environmentPolicy`, точную карту `environmentDefaults` и `environmentApplications`. Чистые прямые прогоны подтверждают применение значения из сборки, а не унаследованную диагностическую маску. Bootstrap-прогоны используют новый закреплённый bootstrap и фиксируют источник политики без выдуманного наблюдения окружения дочернего процесса. Старый PASS с тем же EXE, но без этой политики, выпуск не разрешает. Сохранение личных значений и явных удалений проверяется отдельно от чистой игровой приёмки.

После сохранения реальных отчётов выполните `python -B tools/verify_release_gates.py --candidate $candidate --base-repo $baseRepo` и сохраните JSON-вывод в `tools/qa/update-preservation.json`. Команда сначала требует успешную приёмку настоящего кандидата, затем на копиях отчётов в памяти проверяет запрет устаревшего EXE, пропуска JEI, потери назначений Waypoints, сетевых эффектов, изменений мира, проверки прав, резервной копии, политики серверов и уведомлений. Игровые файлы и отчёты она не меняет. Выпуск требует чистый общий checkout Edition с совместимыми опубликованными base-lock и исходниками контракта; предварительный прогон уведомлений допускается до публикации базы, но не разрешает выпуск.

Для подготовки кандидата зафиксируйте коммит и SHA256 распределительного lock базовой сборки в `tools/base-lock.json`, SHA256 проверенной квитанции сборки в `tools/build-lock.json`, уведомления о распространении каждого мода и их SHA256 в `tools/mod-license-lock.json`. Версия общего bootstrap с поддержкой путей конфигурации экземпляра закрепляется в `tools/bootstrap-lock.json`. `launcher/instance-config.json` удерживает конфигурацию Tectonic в папке игры. Формат каждого lock имеет `schemaVersion: 1`. Поля остальных уровней проверяются по `tools/stage_mod_pack.py`.

```powershell
python tools/stage_mod_pack.py --base-repo $baseRepo --base-candidate $baseCandidate `
    --build-work $work --license-cache $licenseCache --bootstrap $bootstrap --candidate $candidate
```

Запустите кандидат через штатный bootstrap с общим проверенным кешем. Технический клиент сохраняет снимок игры, фиксирует фактически принятые контентные моды и зарегистрированные строки нативных модов, создаёт мир и входит в него повторно. Команда Veinminer и созданный конфиг Dynamic FPS подтверждают запуск модов без собственной строки. Тест Tectonic проверяет путь конфигурации при унаследованной переменной окружения. Проверьте механику модов и открытие сети отдельно. Снимите `library/preview.jpg` из этого прогона и закрепите подтверждённый `library/loaded-mods.json`. Добавьте эти два файла в библиотеку кандидата и закрепите результат `--propose-lock`. Для выпуска требуется чистый checkout и `tools/distribution-lock.json`.

Для проверки самостоятельной подготовки используйте пустой `--cache`, `--bootstrap` и опустите `--minecraft` и `--java`. Сценарий изолирует поиск внешней установки и удаляет унаследованный `JAVA_HOME`.

У предыдущего выпуска с Orbital Laser приёмка была ограничена запуском и меню Windows по выбору игрока; его `--startup-only` и отметки непроверенных механик сохранены как историческое свидетельство. Текущий выпуск требует полного игрового прогона и сетевых проверок ниже. После прогона перенесите `smoke.json`, сетевой `report.json` и `backup-guard.json` в указанные выше файлы `tools/qa/`.

```powershell
python tools/smoke_runtime.py --base-repo $baseRepo --candidate $candidate `
    --controller $controller --qa $qa --bootstrap --cache $cache
python tools/smoke_backup_guard.py --base-repo $baseRepo --candidate $candidate `
    --controller $controller --resources $resources --qa $qa --run-owner $runOwner
python tools/smoke_multiplayer.py --candidate $candidate --controller $controller `
```
